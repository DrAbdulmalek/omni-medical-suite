## 4.4 — استراتيجية إصدارات releases/tags (مقترح فقط)

### المشكلة
لا يوجد نظام tags/releases في omni-medical-suite رغم نضج المشروع. عند نشر تحديثات لـ HF Spaces، لا يمكن معرفة "أي نسخة من الكود تعمل فعليًا على كل Space".

### المقترح
نظام إصدارات بسيط (semver أو تاريخي):

| النمط | مثال | المميزات |
|-------|-------|---------|
| **SemVer** | `v2.3.0` | معياري، واضح، لكن يحتاج قرار "breaking change" |
| **تاريخي** | `v2026.07.12` | بسيط، لا يحتاج تحليل، لكن أقل إفادة |
| **Hybrid** | `v2.3.0-20260712` | كلاهما |

### خطة الإصدار المقترحة (إذا وافق Malek)

```
v1.0.0 — الحالة الحالية (base)
  ├── تُنشأ كـ tag على commit 9052b0c (بعد إصلاح الاستيراد)
  └── كل HF Space يُحدَّث ليشير إلى هذا tag

v1.1.0 — القادمة (بعد رفع تغطية الاختبارات)
  ├── شرط: تغطية اختبارات ≥ 40% على الأقل لحزمة واحدة
  └── يحتوي: إصلاحات Category B + docs consolidation + quality gate

v2.0.0 — مستقبلية (إعادة هيكلة كبرى)
  ├── شرط: تحويل الحزم الـ5 من merged-remnant إلى حزم Python حقيقية
  └── يحتوي: هيكلة imports، اختبارات شاملة، CI/CD كامل
```

### ما يحتاجه Malek لاتخاذ القرار
1. **هل تريد نظام إصدارات فعليًا الآن؟** — أم لاحقًا عندما يصبح المشروع أكثر استقرارًا
2. **أي نمط تفضل؟** — semver (يتطلب تحديد breaking changes) أم تاريخي (أبسط)
3. **هل تريد auto-deploy لـ HF Spaces عند كل tag؟** — يمكن إعداد GitHub Action
